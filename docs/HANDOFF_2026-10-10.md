## Безопасная отмена

Ранее GUI сохранял пути созданных копий/папок и при Undo заново готовил удаление.
Так можно было отправить в Корзину уже отредактированную копию или новую работу
внутри папки. Теперь GUI хранит исходные `Receipt`.

Для Copy/New folder квитанция содержит снимок в памяти: относительный путь,
идентичность объекта, тип, размер, время изменения/создания и атрибуты.
На Windows идентичность — serial тома + file index; нулевой index отклоняется.
На Unix используются device/inode и mode. Для папки сравнивается весь состав,
поэтому новый, удалённый или изменённый дочерний объект блокирует отмену.
Снимок копии снимается до публикации, затем сравнивается с конечным путём.
После `create_dir` отмена разрешается только при снимке пустой папки.

`Receipt::can_undo()` означает наличие защитных сведений, а не обещание,
что объект всё ещё неизменён. Проверка выполняется непосредственно при Undo.
Без снимка/идентификатора операция может быть завершена, но безопасная отмена
недоступна: UI сообщает об этом и сохраняет барьер в стеке, чтобы Ctrl+Z
не пропустил последнее действие и не отменил неожиданно более старое.

Все GUI-отмены вызывают `OperationQueue::undo_completed_audited`: сначала
OS-блокировка исполнителя и SQLite `queued/running`, затем изменение диска
и `finish_undo`. Неаудированный `undo_completed` остаётся низкоуровневым API;
не использовать его для новых GUI-действий. Отказ журнала/блокировки до
исполнения не меняет файлы. Ошибка записи конечного статуса после успешной
операции выводится в stderr и не превращает её в автоматически повторяемый отказ.

Пакет отменяется в обратном порядке. Неудачные квитанции возвращаются в стек;
повторный Ctrl+Z затрагивает только их. Успешные элементы не повторяются.
Move/Rename на одном томе продолжают использовать прежний `completed_stamp`, а не полный
снимок дерева Copy; этот набор изменений не расширяет их контракт.

## Точное восстановление из Корзины

Поиск «самого нового» объекта по папке, отображаемому имени/основе имени и
времени удалён. Windows `PostDeleteItem` сохраняет абсолютное parsing name
именно созданного объекта Корзины. Квитанция связывает его с исходным путём.
Одинаковые основы имён, скрытые расширения и повторные удаления одного пути
не должны менять выбранный объект восстановления.

`IFileOperation` всегда выполняется на новом STA-потоке; COM-интерфейсы
не передаются в MTA-поток GPUI. Callback отдельно различает ошибку действия
и успешное действие без пригодного идентификатора. Положительные Shell-коды
ignored/not handled/pending не считаются завершением.

Перед восстановлением проверяется `symlink_metadata` исходного пути, включая
занятые dangling links. При конфликте квитанция остаётся пригодной для повтора.
Для поздней гонки используется `FOF_RENAMEONCOLLISION`: Shell может восстановить
под свободным именем. Это завершённое восстановление с предупреждением,
а не ошибка с уже израсходованной квитанцией. `UndoOutcome.restored_path`
передаёт реальный путь в UI; `finish_undo` сохраняет его и предупреждение в SQLite.
Тип результата `undo_completed_audited` изменён с `Result<()>` на
`Result<UndoOutcome>` — учитывать в новых вызывающих функциях.

`FOFX_RECYCLEONDELETE` запрашивает Корзину, `FOF_NO_CONNECTED_ELEMENTS`
исключает автоматическое удаление связанных HTML-папок. `FOF_WANTNUKEWARNING`
сохраняет предупреждение Windows о безвозвратном удалении. Это предупреждение,
а не абсолютный запрет такого удаления: не утверждать обратное без отдельной
проверки сценариев больших файлов, отключённой Корзины и иных томов.

## Почему сохранён механизм копирования

Наша очередь, staging на томе назначения, отказ от перезаписи и отмена сохранены.
Прежний поток байтов не переносил дополнительные потоки NTFS. Теперь каждый
файл в Windows-staging создаётся через `CopyFileExW` с `FAIL_IF_EXISTS` и
`COPY_SYMLINK`; ссылки/reparse points всё равно отклоняются заранее.
Флаг разрешения расшифрованной копии не включён.

Исполнитель держит исходный файл открытым с sharing только для чтения и
сверяет метаданные дескриптора с preflight. Активный пишущий процесс может
вызвать отказ копирования; не ослаблять это незаметно. Callback прибавляет
дельту `TotalBytesTransferred`, включая дополнительные потоки, и возвращает
`PROGRESS_CANCEL` по запросу отмены. Очистка readonly выполняется только для
принадлежащего помощнику частичного файла, а не ранее существовавшей цели.

Перед окончательным `MoveFileW` есть проверка отмены после снимка дерева.
Конкурирующая цель не заменяется. Linux-путь отдельного файла остаётся
`persist_noclobber`; safe Move/публикация папок поддерживаются только на Windows.
Показ MiB включает потоки, но `total_bytes` считает основной поток — не строить
процентный индикатор на этих счётчиках без согласования единиц.

## Обновление папок и истории

`DirectoryWatch` наблюдает только видимые папки, без рекурсивного обхода:
максимум 32 корня, очередь 256 уведомлений, до 1024 накопленных путей.
Callback только помещает уведомления в очередь; метаданные и SQLite читает
один рабочий поток. Уведомления доступа игнорируются, а БД и её служебные файлы
исключены из наблюдаемой истории. Dirty-пути публикуются после транзакций истории,
чтобы инспектор не перечитал данные до записи события сохранения.

UI опрашивает изменения каждые 250 мс, сбрасывает затронутые кэши и обновляет
выбранный объект. Dirty-событие, пришедшее во время сканирования списка,
сохраняется до завершения запроса и запускает повторный scan. Номера запросов
защищают от поздних результатов старого списка/инспектора. Начальная подписка
тоже требует повторного сканирования, закрывая промежуток до регистрации notify.

При ошибке/переполнении выставляется `refresh_all` и видимое предупреждение.
Список пересчитывается, но утраченные промежуточные события истории восстановить
невозможно. Это не USN Journal и не гарантия полного журнала изменений.
Автообновление списка работает без включённой истории; кнопка истории отдельно
включает запись метаданных. При активном поиске видимые подписки отключаются;
поисковый `IndexWatch` остаётся отдельным механизмом.

Важно: `HistoryWatch`/`fmctl watch` теперь также не рекурсивны — наблюдают
переданный каталог и непосредственно его записи. Не обещать слежение за всей
вложенной структурой или при закрытом окне. Идентификация реального автора
внешнего сохранения не добавлена; сохраняется учётная запись наблюдателя.

## Границы гарантий

Снимки содержат только метаданные, не содержимое и не хеши файлов. Правка с
сохранением всех наблюдаемых полей может остаться незамеченной. Общая блокировка
координирует экземпляры Filemanager, а не произвольные внешние процессы:
между проверкой снимка и Shell-операцией остаётся окно гонки. Не представлять
защиту Undo как файловую транзакцию или изоляцию от всех внешних изменений.
Квитанции/стек Undo живут в памяти и не восстанавливаются после перезапуска.
SQLite нужен для диагностики; автоматического replay/redo после аварии нет.
Старые версии документов и резервные копии по-прежнему не хранятся.


## Продолжение: проверяемый межтомовой Move

`operations.rs` включает fallback только для `Action::Move` после Windows error
17. Rename и остальные ошибки сохраняют прежний отказ. `cross_volume_move.rs`
пользуется существующей staging-копией, затем `copy_verification.rs` сравнивает
состав дерева и байты всех `$DATA`-потоков (включая ADS каталогов). Чтение блоками
256 КБ, содержимое и хеши после вызова не сохраняются. Перед очисткой повторяются
снимки обеих сторон и проверка отмены. Исходник отправляется в Корзину через
существующий Shell-помощник. После публикации копии отказ не удаляет её.

Undo хранит точный recycle token и `Arc<UndoState>`: после восстановления
сохраняет фактический путь и новый снимок источника. Перед уборкой копии заново
сравнивает содержимое обеих сторон. Повтор частичного Undo не расходует token
второй раз; исчезнувший/изменённый восстановленный источник блокирует очистку.
`PartialUndoError` передаёт фактический восстановленный путь в `finish_undo`,
даже если поздняя очистка не завершилась. Текст ошибки также содержит оба пути.
Снимок восстановленного источника не удалось снять — копия сохраняется,
автоматическое продолжение запрещено. Без точной recycle-квитанции или снимка
копии создаётся существующий барьер Undo.

SQLite получает nullable `phase` в транзакции `IMMEDIATE`, совместимой со старой
схемой. `checkpoint` разрешён только для running job и должен успешно записаться
до следующей мутации. Фазы: `move_copying`, `move_verifying_copy`,
`move_recycling_source`, `undo_restoring_source`, `undo_recycling_copy`.
Незавершённые и failed-задания с фазой остаются в диагностике после перезапуска.
Они не исполняются повторно. GUI использует общий `CopyControl`, показывает
фазу и разрешает отмену передачи; heartbeat сверяет Arc с текущей операцией.

Независимое ревью выявило потерю фактического пути при частичном Undo; исправлено
структурированным результатом ошибки и сохранением destination в журнале.
Проверки: **107 core + 3 CLI теста проходят на Linux**; весь Windows workspace,
включая Desktop и тестовые targets, проходит `cargo check` для MSVC. Windows
тесты здесь лишь компилируются. Linux protocol-тесты вызывают внутренний
межтомовой helper на временных файлах, не имитируют физический второй том.
Новый EXE, ADS/папки и реальные два Windows-тома требуют общей ручной сборки
и [SMOKE_TEST.md §3.3](SMOKE_TEST.md#33-перенос-между-томами-новый-код-windows-smoke-ещё-не-выполнен).

## Пакет 2: замена файлов и наблюдение за очередью

`Plan::prepare_replace` допускает занятое имя только для явного Copy/Move.
`replacement.rs` хранит снимки source/old target и проверяет их после
checkpoint перед recycle. Каталоги, ссылки и один и тот же объект запрещены.
Это не direct overwrite: старый файл отправляется в Корзину, затем исходный
no-clobber transfer создаёт новый. Для Copy сравниваются байты/ADS новой копии;
для Move сохраняется существующий same-volume/cross-volume механизм.
Отказ после recycle старого файла может оставить его прежнее имя свободным.
Программа не обещает автоматического rollback; диагностика должна позволить
ручное восстановление. Квитанция точного old recycle обязательна для продолжения.

Receipt разделяет `replacement::UndoState` через Arc. Undo сначала отменяет
incoming action, сохраняет его Outcome и лишь затем восстанавливает old token.
Ошибка второй стадии не повторяет первую при следующей попытке. Если имя
занято другим приложением, оно не перезаписывается. Стек Undo по-прежнему только
в памяти: после перезапуска доступны диагностические записи, не redo/undo.

`CopyControl::progress` возвращает текущие source/destination и processed/total;
processed означает обработанные задания, включая неудачные, а не успешные.
Preflight-отказы в total подготовленной очереди не включены. `recent(max)`
возвращает не более 100 записей всех статусов, UI запрашивает 30 раз в секунду
на background worker. Epoch панели блокирует запоздалый ответ старого запроса.
Рендер читает только готовые результаты и metadata progress; SQLite из
`toggle_operation_review` на UI-потоке больше не читается.

Точная спецификация и тест-план:
[conflicts-queue](superpowers/plans/2026-10-10-conflicts-queue.md).
Слияние/замена каталогов не реализованы; полноценная очередь нескольких
независимо отправленных GUI-пакетов не добавлена: один активный пакет,
последовательная core-очередь и наблюдение за последними заданиями.

По независимому ревью исправлены два случая потери диагностической информации.
`replacement::RecoveryError` хранит точную old recycle identity и Outcome уже
завершённой incoming Undo-стадии. `finish`/`finish_undo` сохраняют полный текст
в новой nullable колонке `recovery`, отдельно от ограниченного 1200 символами
`error`; old/phase-only схемы мигрируют в той же IMMEDIATE-транзакции.
Partial Undo сохраняет actual incoming restored path в destination даже на
ошибке последующего old restore. На успешном Undo путь old restore — основной,
а предупреждение о позднем переименовании incoming источника сохраняется.
UI показывает recovery вместе с ошибкой. Авария до finish может оставить
только предварительную фазу без точной recycle identity: ручная проверка
Корзины необходима; crash-safe восстановление не обещано.

Проверки пакета 2: 118 core + 3 CLI теста проходят на Linux; полный MSVC
all-targets cross-check прошёл перед публикацией. Windows EXE/Shell/UI
runtime и настоящие два тома по-прежнему требуют отдельного smoke-теста.

## Пакет 3: массовое переименование (11.10)

`core::bulk_rename::preview(paths, template)` возвращает строки и сохраняет
подготовленные `Plan` внутри `RenamePreview`. `can_apply` требует хотя бы
одного изменения и отсутствия ошибок во всех строках; `into_queue` переносит
именно эти планы, не обновляя снимки источников после предпросмотра.
Токены `{stem}`, `{ext}` (с точкой), `{n}` (с 1) подставляются один раз,
в порядке списка. Для папок stem — полное имя, ext пустое. Лимиты: 1000
элементов и 1024 UTF-16 единицы шаблона. No-op строки не исполняются.
Занятые цели, запрещённые Windows-имена, дубликаты, ссылки и пары
родитель/потомок блокируют применение; swap и case-only rename не поддержаны.
На Windows имена сравниваются через `CompareStringOrdinal(ignoreCase)`;
Unicode final sigma тоже проверяется. Linux модель использует uppercase,
поэтому её сравнение не заменяет Windows runtime проверку.

GUI: F2 на группе или кнопка в инспекторе; фоновые проверки после 200 мс,
немедленная очистка старого результата при изменении шаблона и generation
guard при закрытии/повторном открытии. Применение использует общий progress,
Cancel, audited очередь и один Undo для успешных элементов. Группа не
транзакционная: поздний отказ не откатывает уже завершённые переименования.
`RenameReport` сохраняет все квитанции и ошибки группы. GUI показывает каждый
отказ в отдельном прокручиваемом результате, независимо от `recent(30)`;
список закрывается явно/Escape, новое переименование его очищает.
Содержимое файлов, исторические хэши и резервные версии не сохраняются.

Проверки: 125 core + 3 CLI теста на Linux, полный Windows MSVC all-targets
check. Windows-only тесты исполнения/Undo скомпилированы, но здесь не
исполнены. Один первоначальный параллельный Unix Trash тест не получил Undo
квитанцию; последующие полный последовательный и параллельный прогоны
прошли. Причина пока не доказана; Windows использует другой Shell механизм.
Ручной Windows UI/Undo smoke остаётся в итоговом пакете проверки.

## Пакет 4: изолированный предпросмотр (11.10)

`preview_host` запускает тот же EXE с private helper flag до инициализации
GPUI. `--preview-document PATH` открывает отдельный STA/Win32 HWND с
зарегистрированным `IPreviewHandler`; `--preview-thumbnail PATH EDGE` только
получает Shell PNG. Аргументы передаются через Command, без shell parsing.
Документы: PDF/doc/docx/xls/xlsx/ppt/pptx/rtf/odt/ods/odp <=64 MiB,
Stream/File/Item initialization с STGM_READ, host frame/site, resize,
raw S_OK accelerator handling, Unload/SetSite(None)/COM cleanup.
Microsoft contract: https://learn.microsoft.com/en-us/windows/win32/shell/building-preview-handlers

Обработчик загружается in-process внутри child: основной менеджер не грузит
DLL провайдера. Нужен установленный совместимый 64-bit provider; документ не
обещает preview на чистой Windows или с одним 32-bit Office. GUI показывает
ошибку отдельно и сохраняет обычное открытие файла. Paging зависит от provider.
PreviewProcess владеет child и Job Object (256 MiB per-process, kill-on-close).
Закрытие/замена/Drop прекращают owned child; закрытие окна менеджера также
инвалидирует ожидающий launch. Job — ограничение ресурсов, не security sandbox;
инициализация provider получает read-only режим, но сторонний DLL не является
кодом, который мы контролируем. Неподдержанные/большие файлы открываются обычно.

Миниатюры: child deadline 5s, edge 1..512, checked RGBA до 1 MiB,
GetDIBits требует все строки. GPUI получает только проверенный PNG <=2 MiB
с dimensions <=edge; прямой decoder исходного JPEG/TIFF/GIF убран.
Уникальный NamedTempFile и atomic persist исключают общий partial writer;
кэш собственных PNG обслуживается до 256 файлов/64 MiB. Shell apartment
балансируется на каждом выходе. Данные исторических версий файлов не хранятся.

Inspector: один metadata/history worker и отдельно один thumbnail worker на
окно, coalescing по последнему выбору и generation/path guards. Старый результат
сразу очищается. Thumbnail/provider timeout не задерживает текст/историю.
Проверки filesystem/SQLite/COM не выполняются в GPUI callbacks.

Исправлен воспроизведённый Unix capture: before snapshot сравнивает пару
(trash id,original path), поскольку concurrent restore освобождает id от другого
исходника. Regression на старом predicate дал None, новый дал правильный token;
параллельный полный suite после исправления прошёл. Same-path ambiguity по-прежнему
выключает Undo. Windows exact Shell callback не менялся.

Проверки после исправлений ревью: 129 core unit + 5 core integration + 3 CLI;
полный MSVC workspace/all-targets check. Реальные handlers, Job runtime,
Win32/GPUI interaction и скриншоты требуют итогового Windows EXE smoke.

Финальное ревью: PNG проходит полный decode с limits до передачи GPUI, включая
проверку IDAT; допустимый 512x512 RGBA проверен regression. Windows child создаётся
CREATE_SUSPENDED, назначается в Job и только затем возобновляется. При ошибке
назначения/возобновления запрашивается kill; Child.wait всегда в отдельном reaper,
включая Drop/замену/закрытие. Unix реальные kill/deadline/reap тесты прошли;
Windows suspension тест только скомпилирован. UI дефект «самостоятельно закрытое
окно preview сохраняет статус „открыто“» исправлен 11.10: инспектор опрашивает
`PreviewProcess::exited()` раз в 500 мс (неблокирующий try_wait, без GPUI-блокировок)
и сбрасывает состояние с понятным статусом. Перечень Windows runtime проверок — в smoke.

## Пакет 5: интерфейс (11.10)

`core/interface.rs` — чистая политика команд и Preferences. `desktop/interface.rs`
— палитра/настройки и guarded marquee; `theme::rgb` отображает семантические цвета
на светлую или тёмную палитру, включая gpui-component input/menu/scrollbar colors.
Ctrl+K ищет русские названия по всем введённым словам; UI использует прежние методы
действий и audited executor. Контекст Input в палитре переопределяет up/down/
Enter/Escape; остальные действия списка блокируются при открытом overlay.
Настройки: light/show_hidden/show_sidebar/show_inspector, отдельный draft,
сохранение SQLite вне UI, apply только после успеха, возврат фокуса списку.
Сеанс и miller_mode по-прежнему находятся в workspace; временные переключатели
панелей/скрытых не записывают preference сами по себе — сохрани их в «Настройках».

`Tab.pinned` — защита закрытия, не фиксация пути; порядок остаётся произвольным.
Browser.close_tab / close_other_tabs единообразно учитывают pinned, включая
Ctrl+W/среднюю кнопку/контекстные меню. workspace_tabs мигрирует в BEGIN IMMEDIATE,
добавляя pinned DEFAULT 0; старые профили сохраняются. interface_preferences
хранит singleton row; значения вне 0/1 считаются ошибкой, не приводятся к true.

`selection::marquee_rows` — checked pure geometry (28px, viewport + scroll).
Жест хранит Arc снимка/индексов, folder/side/tab/sort/filter/mode/scroll/bounds.
Рамка начинается на пустом месте или правом 12px gutter текущей папки панели;
ancestor columns сначала активируются кликом. Invalid snapshot/layout отменяет
жест; Ctrl объединяет с исходным выбором, Esc возвращает его. Новые filesystem
проверки/навигация в жесте отсутствуют; выделение не исполняет файловых действий.
Обычный выбор вычисляется только по пересечённым строкам; Ctrl merge сохраняет
порядок отображения. Автопрокрутка не реализована, прокрутка отменяет жест.

Native baseline 129 core+5 integration+3 CLI. После доработок: 129 core+13
integration+3 CLI, Windows workspace/all-targets MSVC check PASS. Клавиатура,
контраст и реальный mouse routing проверяются в финальном Windows smoke.

После ревью палитра использует predicate `CommandPalette > Input`: `&&` GPUI
применяет к одному узлу и не подходит к ancestor/child context. Script
`tools/check-interface-bindings.py` компилирует реальный GPUI 0.2.2 parser из
cached registry в минимальном host, проверяет 4 клавиши и ранний guard повторного
открытия настроек. Parser regression упал до исправления, после него прошёл;
это не тест реального окна. Нужны CARGO_HOME/RUSTUP_HOME и cached anyhow.
Повторный Ctrl+, при открытом draft или save теперь сохраняет прежний диалог.
`WorkspaceStore::open_with_preferences` не теряет ошибки открытия/повреждения
SQLite; defaults применяются с видимой диагностикой. Core regression на malformed
DB прошёл. `selection::visible_indices` — общий порядок/hidden/filter policy;
marquee сверяет Arc эффективных индексов. При переключении на другую панель
с активным фильтром первый клик только фокусирует её; рамку начинают следующим
жестом, когда новый filter view уже отображён. Старый выбор другой панели очищается.
